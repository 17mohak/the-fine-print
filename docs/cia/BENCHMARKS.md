# Benchmarks — A1 KMP and A2 Bloom filter

All runs were made with nothing else using the CPU; an earlier run contaminated by a concurrent test run was
discarded. Raw data is committed in `cia/cia-bench/results/`.

- **Run 1 (2026-11-20):** KMP and the first Bloom implementation (odd step).
- **Run 2 (2026-11-21):** Bloom after the probe-sequence fix (coprime step; see
  [A2_BLOOM_FILTER.md](A2_BLOOM_FILTER.md)), with a more robust JMH configuration and five hash seeds for the
  false-positive experiment.

**The Bloom figures in this report are from run 2.** Run-1 Bloom figures are kept only for comparison.

## A1 — KMP vs naive vs JDK `String.indexOf` (µs per "find all occurrences", lower is better)

Each search finds every overlapping occurrence of one pattern in one text. KMP and naive work on `int[]` code
points; `indexOf` works on the `String`. Conversion is excluded from timing.

**Ordinary input** (prose-like text, pattern excerpted from it):

| m | n | KMP | naive | `indexOf` |
|---|---|---|---|---|
| 8 | 10,000 | 17.9 | 34.7 | **2.0** |
| 8 | 100,000 | 334.0 | 501.2 | **15.3** |
| 8 | 1,000,000 | 3,407 | 5,272 | **183.7** |
| 64 | 10,000 | 16.1 | 31.0 | **1.6** |
| 64 | 100,000 | 190.3 | 386.4 | **15.5** |
| 64 | 1,000,000 | 2,918 | 3,546 | 2,716 |
| 512 | 10,000 | 26.8 | 32.4 | **1.7** |
| 512 | 100,000 | 261.5 | 506.3 | **15.7** |
| 512 | 1,000,000 | 3,991 | 4,194 | 3,286 |

**Adversarial input** (text `a…a`, pattern `a…ab`; no match exists):

| m | n | KMP | naive | `indexOf` |
|---|---|---|---|---|
| 8 | 10,000 | 38.2 | 78.2 | **7.4** |
| 8 | 100,000 | **385.9** | 736.9 | 1,319 |
| 8 | 1,000,000 | **3,893** | 9,163 | 12,713 |
| 64 | 1,000,000 | **3,644** | 27,772 | 43,206 |
| 512 | 10,000 | **39.1** | 1,833 | 2,908 |
| 512 | 100,000 | **360.5** | 19,291 | 32,485 |
| 512 | 1,000,000 | **3,389** | 185,511 | 347,890 |

### What this shows
- **The baseline wins on ordinary text.** `String.indexOf` is a vectorised HotSpot intrinsic. At n ≤ 100k it is
  about 9–20× faster than our KMP. At n = 1M with longer patterns the gap narrows to within the error bars. Our
  KMP is roughly 1–2× faster than naive on ordinary text, since naive usually fails on the first symbol.
- **KMP's guarantee is real.** On adversarial input KMP's time depends only on n: about 3.4–3.9 ms at n = 1M for
  every m. Naive and `indexOf` grow with m, because both are O(n·m) in the worst case. At n = 1M and m = 512, KMP
  is about **55× faster than naive and about 100× faster than `indexOf`**.
- **Interpretation for the product:** production quote verification uses a standard library search, and
  quotes are short against ordinary text, so KMP is not needed for speed there. KMP is the right choice when
  inputs may be hostile (for example, model-generated quotes engineered to be pathological) or a worst-case bound
  is required. This matches the CIA matrix's stated expectation ("expect JDK `indexOf` to be faster on typical
  text").

## A2 — Bloom filter vs `HashSet<Long>` (run 2, coprime-step probe sequence)

### False-positive rate: measured vs theoretical

`results/bloom-experiment.csv`: keys `0..n−1` inserted; 1,000,000 never-inserted keys probed; five seeds per
configuration. *Theory* is the textbook `(1 − e^{−kn/m})^k`. For this probe scheme it is an **approximation**
(see "Qualification" in A2_BLOOM_FILTER.md), so the measured column is the evidence.

| n | bits/elem | k | theory | measured mean (5 seeds) | seed s.d. | min–max | mean ÷ theory | run 1, odd step (seed 7) |
|---|---|---|---|---|---|---|---|---|
| 10,000 | 6 | 4 | 5.606 % | 5.655 % | 0.028 | 5.617–5.684 % | 1.009 | 5.612 % |
| 10,000 | 10 | 7 | 0.819 % | 0.813 % | 0.010 | 0.800–0.824 % | 0.993 | 0.807 % |
| 10,000 | 14 | 10 | 0.120 % | 0.121 % | 0.003 | 0.117–0.124 % | 1.010 | 0.115 % |
| 100,000 | 6 | 4 | 5.606 % | 5.604 % | 0.026 | 5.576–5.638 % | 1.000 | 5.584 % |
| 100,000 | 10 | 7 | 0.819 % | 0.814 % | 0.006 | 0.804–0.817 % | 0.994 | 0.815 % |
| 100,000 | 14 | 10 | 0.120 % | 0.121 % | 0.006 | 0.114–0.128 % | 1.010 | 0.124 % |
| 1,000,000 | 6 | 4 | 5.606 % | 5.594 % | 0.022 | 5.567–5.621 % | 0.998 | 5.588 % |
| 1,000,000 | 10 | 7 | 0.819 % | 0.825 % | 0.007 | 0.817–0.832 % | 1.006 | 0.809 % |
| 1,000,000 | 14 | 10 | 0.120 % | 0.120 % | 0.004 | 0.116–0.126 % | 1.002 | 0.119 % |

(s.d. in percentage points.)

- **Measured:** the mean over seeds is within ±1 % (relative) of the textbook value in every configuration, and
  the seed-to-seed spread is of the order of the binomial sampling error (about 0.009 percentage points at
  p = 0.8 % with 1M probes).
- **Effect of the fix on FPR:** none detectable. The run-1 odd-step values lie within the run-2 seed range or
  within sampling error of it. All moduli here are `m = n × b` with odd factors (for example `10⁶ × 10 = 2⁷·5⁷`),
  where an odd step could share the factor 5. The theory says that costs a key distinct positions only when
  `m / gcd(b, m) < k`, which for these large m almost never happens, so a detectable FPR difference was not
  expected. The fix matters for **correctness guarantees** (distinct positions for every m, no overflow), not
  for the average rate at these sizes.
- **Sizing formulas:** `m = −n ln p / (ln 2)²` and `k = (m/n) ln 2` remain valid design rules for this
  implementation **at the sizes measured**, as shown by measured ≈ theory. They are not exact for this scheme.

### Memory

| n | Bloom bytes (10 bits/elem) | Bloom B/elem | HashSet bytes (approx.) | HashSet B/elem |
|---|---|---|---|---|
| 10,000 | 12,504 | 1.25 | 625,616 | 62.6 |
| 100,000 | 125,000 | 1.25 | 7,759,160 | 77.6 |
| 1,000,000 | 1,250,000 | 1.25 | 65,465,048 | 65.5 |

Across all configurations the Bloom filter uses about **36–103× less memory** (50–62× at 10 bits/element). Bloom
bytes are exact (bit-array payload). HashSet bytes are approximate (used-heap delta after forced GCs) and are
unchanged by the fix.

### Throughput (JMH run 2: operations per µs, higher is better; batches of 1,024, half present and half absent)

| n | bits/elem | Bloom query | HashSet query | Bloom insert | HashSet insert |
|---|---|---|---|---|---|
| 10,000 | 10 | 8.11 ± 0.70 | 188.85 ± 7.16 | 8.44 ± 0.46 | 46.60 ± 1.48 |
| 100,000 | 10 | 7.10 ± 0.39 | 195.48 ± 9.67 | 8.74 ± 0.38 | 45.45 ± 1.56 |
| 1,000,000 | 10 | 6.07 ± 0.45 | 172.97 ± 4.67 | 8.35 ± 0.46 | 46.34 ± 1.45 |
| 1,000,000 | 6 | 5.48 ± 0.42 | 178.91 ± 2.90 | 8.89 ± 0.67 | 46.68 ± 2.28 |
| 1,000,000 | 14 | 4.30 ± 0.15 | 173.15 ± 10.21 | 7.77 ± 0.71 | 46.43 ± 1.96 |

(All 36 rows are in `jmh-bloom-results.json`.)

- **HashSet is about 23–40× faster per query and about 5–6× faster per insert.**
- **Run 1 against run 2 (performance cost of the fix):**
  - Bloom query throughput fell from about 18–29 to about 4–8 ops/µs (3–4×).
  - Bloom insert fell from about 11–23 to about 8–9 ops/µs.
  - In the same comparison HashSet changed by only about 20 %, so most of the Bloom drop comes from the code
    change, not the machine.

  The likely cause is the per-key step computation: Euclid's `gcd`, a chain of 64-bit divisions, plus two
  unsigned remainders. Run 1 used one remainder per probe and no gcd. This was **not profiled further**, so
  the attribution is an inference.
  A cheaper correct alternative would be to factorise `m` once at construction and test coprimality against its
  few distinct prime factors, or to size m to a prime so that every step in `[1, m − 1]` is coprime. Either is a
  change in scope, left for review.
- **Conclusion unchanged:** at these sizes the Bloom filter is a memory tool, not a speed tool. That is why
  production uses an exact set (ARCHITECTURE_OVERVIEW section 2).

## Known limitations of these measurements
- Short JMH configuration and wide confidence intervals (see the caveat above).
- Single machine, Windows, laptop CPU (frequency scaling not controlled).
- HashSet memory is an approximation (GC-based), not an object-graph measurement.
- The Bloom build time in the CSV (`bloomBuildMillis`) is a single cold measurement, indicative only. Use the
  JMH insert rows for throughput.
- Synthetic ASCII text only for KMP throughput; Unicode behaviour is covered by tests, not benchmarks.
- The FPR experiment uses sequential integer keys for both inserted and probe sets; other key distributions
  were not measured.
- The throughput regression of the probe-sequence fix was measured but not profiled.
